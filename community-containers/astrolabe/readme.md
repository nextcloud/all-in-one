## Astrolabe

This container adds an **agent to the Nextcloud Assistant's "Chat with AI"** that can look
things up in your own Nextcloud — your files, notes, calendar, contacts and Deck cards —
and answer with links back to what it used.

Normally that needs Nextcloud's **Context Agent** app, which is an **ExApp**: it only runs
through AppAPI and a deploy daemon (HaRP, or the deprecated Docker Socket Proxy), which
means giving Nextcloud access to a Docker socket. This container needs **none of that**.
The [Astrolabe](https://apps.nextcloud.com/apps/astrolabe) app registers itself directly as
the provider for Nextcloud's own `core:contextagent:interaction` task type, and talks to the
[nextcloud-mcp-server](https://github.com/cbcoutinho/nextcloud-mcp-server) container that
this adds. No AppAPI, no ExApp, no Context Chat, no Docker socket.

### What gets set up for you

Enabling this container installs and enables the `oidc`, `astrolabe` and `assistant` apps,
points Astrolabe at the MCP server, and turns the agent on. There is nothing to configure
by hand.

Two OIDC clients are registered for you, both with credentials generated by AIO:

- a **public** client for the Astrolabe app, which mints a short-lived, per-user token for
  each request it makes to the MCP server;
- a **confidential** client for the MCP server itself (client id + secret), which it uses
  for OIDC discovery, key retrieval and token validation. This is registered statically on
  purpose — the `oidc` app deletes dynamically registered clients after about an hour,
  which would silently break the connection.

### Two URLs, and why

The MCP server is addressed two different ways, and they are deliberately not the same:

- **`http://nextcloud-aio-astrolabe-mcp:8000`** — the internal Docker network address.
  Nextcloud uses this to talk to the MCP server, so that traffic never leaves the host.
- **`https://mcp.$NC_DOMAIN`** — the public address. It is the audience of every token the
  MCP server accepts, the OAuth callback address, and the address any MCP client outside
  your server connects to.

**The Nextcloud Assistant agent works either way**, because Nextcloud reaches the server
over the Docker network. The public address only matters if you want to connect an
**external MCP client** — Claude Desktop, an IDE, and so on — or use the MCP server's own
web UI.

If you want that, you need to point a reverse proxy at **port 8000** of this server for the
subdomain `mcp.$NC_DOMAIN`, and add the matching DNS record. Only `mcp.$NC_DOMAIN` is
supported — if Nextcloud runs on `your-domain.com`, the MCP server must be reachable at
`mcp.your-domain.com`. See
https://github.com/nextcloud/all-in-one/tree/main/community-containers/caddy or
https://github.com/nextcloud/all-in-one/blob/main/reverse-proxy.md.

You can skip all of that if you only want the Assistant agent.

### Requirements — read this first

- **You must supply the language model.** Astrolabe does the *retrieval*; every generated
  word comes from a Nextcloud TaskProcessing provider that you install and configure. It
  must support **tool calling** — the task type `core:text2text:chatwithtools`. The usual
  choice is the **OpenAI and LocalAI integration** (`integration_openai`), pointed at
  OpenAI, at any compatible endpoint, or at a local model. The
  [local-ai](https://github.com/nextcloud/all-in-one/tree/main/community-containers/local-ai)
  community container is one way to keep that local.
  Check **Administration → Artificial intelligence**: **Chat with tools** must list at least
  one provider. Without one, the agent stays unavailable.
- **Each user provisions themselves once.** Open the **Astrolabe** app's personal settings
  and provision access. Until a user does that, the agent cannot act on their behalf.
- **Nextcloud 32–34.** That is the range the Astrolabe app supports.

### What this container does *not* do

Astrolabe's **semantic search is switched off** in this container, and so is background
indexing. Nothing of yours is embedded, indexed or copied into a vector database — the
agent reads through Nextcloud's own APIs, live, as the user asking the question. The
trade-off is that the Astrolabe app's own search page has no index behind it, and the agent
finds things by browsing rather than by meaning. Semantic search (which needs a vector
database and an embedding model) is planned as a follow-up.

### Permissions

The agent is given **read-only** scopes:

```
files.read notes.read webdav.read calendar.read contacts.read deck.read
```

The MCP server hides every tool those scopes do not grant, so this — not the app list — is
the real limit on what the agent can do. It cannot change your content. An administrator can
widen it, but think hard first: adding a write scope lets the assistant modify data without
asking.

```
sudo docker exec --user www-data -it nextcloud-aio-nextcloud php occ config:app:set astrolabe agent_scopes --value='files.read notes.read ...'
```

Note that the container resets this value to the read-only default every time the Nextcloud
container starts, so a change made this way is not permanent.

### Checking that it works

```
# what a given user's agent can actually see
sudo docker exec --user www-data -it nextcloud-aio-nextcloud php occ astrolabe:mcp-probe alice \
    --scopes "files.read notes.read webdav.read calendar.read contacts.read deck.read"
```

If that connects and lists tools, the agent will work for that user. Then open
**Assistant → Chat with AI** and ask about something you know is there.

### Backups

The `nextcloud_aio_astrolabe_mcp_data` volume is included in AIO's backup. It holds the
encrypted per-user credentials the MCP server uses to act on each user's behalf; losing it
means every user has to provision again.
